# JavaScript Attacks — Medium

De ontwikkelaar vertrouwt niet meer op het simpel omdraaien van het woord en kiest een "echt" algoritme: ROT13. Elke letter schuift dertien plaatsen op in het alfabet. Dat klinkt als versleuteling, maar het draait nog steeds volledig in jouw browser.

## 1. Predict (Voorspel)

Het formulier heeft weer een tekstvak (**Woord**) en een verborgen `token`-veld. Bij het verzenden roept JavaScript in de pagina een functie `rot13` aan: die codeert het woord met ROT13 en zet de uitkomst in het token-veld. De server keurt de poging goed als het woord `success` is én het token de ROT13-versie van dat woord is.

**Vraag:** Je typt `success` in het tekstvak en klikt op Submit. Werkt de aanval nog, nu de ontwikkelaar ROT13 gebruikt in plaats van het woord omdraaien?

<details>

<summary>Antwoord</summary>

Ja, het werkt nog steeds. Het maakt niet uit welk algoritme de ontwikkelaar kiest — reversen, ROT13 of iets ingewikkelders — zolang de browser het token berekent, levert jouw browser zelf een geldig token aan. Je hoeft ROT13 niet eens te kennen. Je typt `success` en de inline JavaScript rekent `fhpprff` (ROT13 van `success`) voor je uit.

</details>

## 2. Run (Uitvoeren)

Start het lab, typ `success` in het tekstvak en klik op Submit.

Je ziet de melding `Correct! Token gevalideerd.` — zonder dat je ooit hoefde te weten wat ROT13 is.

## 3. Investigate (Onderzoeken)

Open F12 → **Elements** (of **Sources**) en bekijk het `<script>` onder aan het formulier.

**Vraag:** Hoe berekent de pagina het token uit het woord? Wat betekent dat voor de veiligheid?

<details>

<summary>Antwoord</summary>

Er staat een functie `rot13` in de pagina die elke letter dertien plaatsen opschuift. Bij het verzenden roept het script `rot13` aan op het woord en zet de uitkomst in het verborgen `token`-veld. Het "geheime" algoritme staat gewoon leesbaar in de broncode, dus iedereen kan het namaken. ROT13 is bovendien geen versleuteling maar een verschuiving die je zo terugdraait. Omdat de browser het token maakt, bepaalt de gebruiker het token — niet de server.

:::

</details>

## 4. Modify & Make (Aanpassen & Maken)

Verander het woord in het tekstvak naar iets anders dan `success` (bijvoorbeeld `hallo`) en verzend. Verzend daarna nog eens met `success`.

**Vraag:** Waarom lukt alleen `success`, ook al maakt de browser voor elk woord netjes een passend ROT13-token?

<details>

<summary>Antwoord</summary>

De server controleert náást het token ook of het woord letterlijk `success` is. Het token-veld voegt daar niets aan toe, want het wordt toch in de browser gemaakt. ROT13 is alleen een dun laagje obfuscatie: het maakt de code iets minder herkenbaar, maar verandert niets aan de kern. De echte controle blijft "is het woord success?".

</details>

## 5. ✓ Wat moest je zien?

:::tip[Controle]
- Het invullen van `success` slaagt meteen, net als op Low, ondanks het "sterkere" ROT13-algoritme.
- In de paginabron zie je de functie `rot13` die het token uit het woord berekent.
- Alleen `success` wordt goedgekeurd, omdat de server ook het woord zelf controleert — het client-side token voegt geen beveiliging toe.
:::

## 6. Er gaat iets mis...

De ontwikkelaar dacht: als ik het algoritme maar ingewikkelder maak, kraakt niemand het meer. Dat is "Security by Obscurity" — beveiliging die leunt op geheimhouding van de methode in plaats van op een echt geheim.

Het probleem: de browser moet de code kunnen uitvoeren, dus staat de methode altijd leesbaar in de pagina. ROT13, base64 of een ge-obfusceerde functie met een onleesbare naam maken het voor een mens even lastiger te lezen, maar de browser voert het gewoon uit en berekent het token voor je. Een aanvaller hoeft de code niet eens te begrijpen — die typt `success` en laat de pagina het werk doen. **Never trust the client.**
