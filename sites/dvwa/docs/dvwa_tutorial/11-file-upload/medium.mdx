# File Upload — Medium

De ontwikkelaar merkt dat er PHP-bestanden binnenkomen en voegt een controle op het bestandstype toe.

## 1. Predict (Voorspel)

De server controleert nu het MIME-type van het geüploade bestand:

```php
$uploaded_type = $_FILES[ 'uploaded' ][ 'type' ];

if( ( $uploaded_type == "image/jpeg" || $uploaded_type == "image/png" ) ) {
    // Bestand opslaan
} else {
    echo "Je bestand was geen afbeelding.";
}
```

**Vraag:** Waar komt de waarde van `$_FILES['uploaded']['type']` vandaan — van de server of van de browser? Wat betekent dat voor de betrouwbaarheid van deze controle?

<details>

<summary>Antwoord</summary>

De `Content-Type`-header komt van de **browser (client)** in het HTTP-verzoek. De server vertrouwt blind wat de browser zegt. Verander je die waarde van `application/php` naar `image/jpeg` voordat het verzoek de server bereikt, dan ziet de server een "afbeelding" en accepteert hij het bestand — ook al is het een PHP-script.

</details>

> **Labbeperking:** In dit lab kies je de Content-Type zelf uit een dropdown, zodat je het effect meteen ziet. Op een echte DVWA is de Content-Type een echte HTTP-header die je onderschept en vervalst met een proxy als [Burp Suite](/docs/dvwa_installatie).

## 2. Run (Uitvoeren)

Start het lab en bekijk het formulier: naast de bestandsnaam kies je een MIME-type.

<DvwaLab module="file_upload" level="medium" />

Vul `foto.jpg` in met MIME-type `image/jpeg` — dat werkt. Kies daarna `shell.php` met MIME-type `application/php` en zie dat de server het weigert.

## 3. Investigate (Onderzoeken)

Bekijk in de broncode (**Bekijk broncode**) hoe de server beslist.

**Vraag:** Waarop kijkt de server precies — de inhoud van het bestand, of de meegestuurde Content-Type? En wie bepaalt die Content-Type?

<details>

<summary>Antwoord</summary>

De server kijkt alleen naar de meegestuurde Content-Type, niet naar de echte inhoud. En die Content-Type bepaal jij, als client. In dit lab is dat de dropdown; in een echt verzoek is het een header die je vrij kunt kiezen. De server controleert nergens of het bestand écht een JPEG is.

</details>

## 4. Modify & Make (Aanpassen & Maken)

Laat de server `shell.php` accepteren door een afbeeldings-MIME mee te sturen.

<details>

<summary>Tip</summary>

Combineer een `.php`-bestandsnaam met een MIME-type dat wél op de toegestane lijst staat.

</details>

<details>

<summary>Antwoord</summary>

Vul `shell.php` in als bestandsnaam en kies `image/jpeg` als MIME-type. De server accepteert het bestand en meldt tegelijk: "PHP-extensie gedetecteerd — MIME-type was image/jpeg, maar de extensie is nog steeds .php". De MIME-controle is dus omzeild. Op een echte DVWA navigeer je daarna naar de upload-URL om de code uit te voeren.

</details>

## 5. ✓ Wat moest je zien?

:::tip[Controle]
- Met MIME `application/php` weigert de server `shell.php`.
- Met MIME `image/jpeg` accepteert de server ditzelfde `shell.php` — de controle is omzeild.
- De server keek alleen naar de (door jou gekozen) Content-Type, niet naar de echte inhoud.
:::

## 6. Er gaat iets mis...

Op een echte DVWA denk je de header aan te passen via F12 → **Network**, verstuurt, en de server weigert `shell.php` alsnog. Het Network-tabblad *laat* het verzoek alleen zien — het onderschept het niet. Als de header daar verschijnt, is het verzoek allang verzonden en bewerk je een kopie achteraf.

Om de header te veranderen vóórdat hij de server bereikt, heb je een proxy nodig die het verzoek vasthoudt: Burp Suite (of "Edit and Resend" in Firefox). In dit lab is die stap voor je vereenvoudigd tot de dropdown, zodat je het idee kunt uitproberen zonder proxy.
