# Online zetten: je domein met HTTPS

Over `http` gaat alles leesbaar over de lijn. Wie op hetzelfde wifi zit, of ergens onderweg een kabel beheert, kan meelezen: het wachtwoord waarmee een bezoeker inlogt, en de cookie met zijn sessie-id. Met `https` is het versleuteld, en weet de browser bovendien zeker dat hij met jouw server praat en niet met een die zich voor jou uitgeeft.

Daarvoor heb je een **certificaat** nodig: een bewijs, ondertekend door een bekende partij, dat jouw server bij jouw domeinnaam hoort. Caddy vraagt er zelf een aan, gratis, bij Let's Encrypt, en vernieuwt het op tijd.

## Je naam in de Caddyfile

Open de Caddyfile op de server:

```bash
sudo nano /etc/caddy/Caddyfile
```

Vervang `:80` door je domeinnaam:

```text
gastenboek.voorbeeld.nl {
	reverse_proxy 127.0.0.1:8000
}
```

```bash
sudo systemctl reload caddy
```

Caddy ziet een naam in plaats van een poort, en doet nu drie dingen: hij vraagt een certificaat aan voor die naam, hij luistert op 443 voor `https`, en hij stuurt elk verzoek op `http` door naar `https`. Open `https://gastenboek.voorbeeld.nl` op je telefoon. Je site opent zonder waarschuwing over de verbinding.

Twee dingen moeten kloppen voordat het lukt: het A-record wijst naar je server ([les 7](site:fullstack/docs/online/server/huren)), en poort 80 en 443 staan open in de firewall ([les 8](site:fullstack/docs/online/server/dichtzetten)). Let's Encrypt komt via poort 80 controleren dat de naam echt bij jouw server hoort.

## De cookie alleen over https

Nu je site `https` heeft, kan de sessie-cookie de vlag `secure` krijgen: dan stuurt de browser hem nooit meer over een onversleutelde verbinding. Wat `secure` doet, staat in de praktijkles van [Cookies afschermen](site:fullstack/docs/veiligheid/cookies/praktijk). Zet het bij `set_cookie` in je `/inloggen`:

{/* niet-compileren: alleen de set_cookie uit /inloggen, het endpoint eromheen staat in Cookies afschermen */}

```python
    antwoord.set_cookie(
        key="sessie_id",
        value=sessie_id,
        max_age=60 * 60 * 24 * 30,
        httponly=True,
        samesite="lax",
        secure=True,
    )
```

Op je eigen computer blijft het werken: Chrome en Firefox laten een `secure`-cookie op `127.0.0.1` en `localhost` toch door. Hoe de nieuwe code op de server komt, is de volgende les.

## Er gaat iets mis

### Geen certificaat

In `sudo journalctl -u caddy -n 30` staan regels met `challenge failed` of `could not get certificate`, en de browser zegt dat de verbinding niet veilig is.

**Oorzaak:** Let's Encrypt kon niet controleren dat de naam bij jouw server hoort. Meestal wijst het A-record nog niet naar je server, of poort 80 is dicht. Een derde oorzaak zie je niet met `ping`: een oud `AAAA`-record (een IPv6-adres) van de parkeerpagina van je domeinbedrijf. Let's Encrypt kiest dan dat adres, en komt niet bij jouw server.

**Oplossing:** controleer met `getent ahosts gastenboek.voorbeeld.nl` alle adressen van je naam: staat er een adres tussen dat niet van jouw server is, haal dan dat record weg bij je domeinbedrijf. Kijk met `sudo ufw status` of 80 en 443 openstaan. Wacht daarna even: Caddy probeert het zelf opnieuw. Herstart hem niet steeds: Let's Encrypt laat maar een paar mislukte pogingen per uur toe.

### Je site werkt niet meer op het IP-adres

Op `http://203.0.113.10` zegt de browser dat de verbinding niet veilig is, of hij komt niet verder.

**Oorzaak:** met een naam in de Caddyfile stuurt Caddy elk verzoek op `http` door naar `https`, ook dat met het IP-adres. Voor het IP-adres heeft hij geen certificaat.

**Oplossing:** open je site met je domeinnaam. Dat is ook het adres dat je aan anderen geeft.

## Opdrachten

### Opdracht 1: Run - HTTPS voor je site

Zet je domeinnaam in de Caddyfile, laad Caddy opnieuw, en open je site met `https`. Klik in de adresbalk op het pictogram voor het adres: wie heeft het certificaat ondertekend, en tot wanneer is het geldig?

<details>
<summary>Antwoord</summary>

Als uitgever staat er Let's Encrypt, meestal met een korte naam als `E5` erbij, of ZeroSSL: die gebruikt Caddy als Let's Encrypt het even niet doet. Het certificaat is hooguit drie maanden geldig, en Caddy vernieuwt het vanzelf ruim voordat het afloopt.

</details>

### Opdracht 2: Modify - Nooit meer http

Caddy stuurt `http` door naar `https`, maar de allereerste keer gaat het verzoek nog onversleuteld. Met de kop `Strict-Transport-Security` vertel je de browser: gebruik voor deze naam voortaan altijd `https`, ook als iemand `http` typt. Zet in je Caddyfile, binnen de accolades onder `reverse_proxy`:

```text
	header Strict-Transport-Security "max-age=86400"
```

Laad Caddy opnieuw. Hoe zie je in de ontwikkelaarstools dat de kop meekomt?

<details>
<summary>Tip</summary>

De koppen van een antwoord staan in het tabblad Netwerk, bij een verzoek. Zie [Kijken wat de browser doet](site:fullstack/docs/FastAPI/eerste-server/devtools-netwerk).

</details>

<details>
<summary>Antwoord</summary>

Klik in Netwerk op het verzoek van de pagina. Onder de koppen van het antwoord staat `strict-transport-security: max-age=86400`. `max-age` is in seconden: een dag lang gebruikt de browser alleen nog `https` voor je naam. Grote sites zetten hier een jaar (`31536000`), maar begin klein: een browser die de kop kent, gaat die tijd niet terug naar `http`, ook niet als je server later weg is of iets anders draait.

</details>
