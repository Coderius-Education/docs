# Online zetten: een nieuwe versie uitrollen

<Voorkennis items={[{site: 'editor', to: '/git/pull-clone/stap-2-pull', label: 'Nieuwe commits ophalen met git pull'}]} />

Je site staat online. Nu verander je iets, bijvoorbeeld de `secure=True` uit de vorige les. Je werkt zoals altijd in Ubuntu op je laptop: veranderen, testen met `docker compose up -d --build`, en een commit naar GitHub. Daarna haalt de server de nieuwe versie op.

## Twee stappen op de server

```bash
cd ~/gastenboek
git pull
docker compose up -d --build
```

- `git pull` haalt de nieuwe commits op.
- `docker compose up -d --build` bouwt een nieuw image en vervangt de container. Kwam er niets bij in `requirements.txt`, dan staat de pip-stap er als `CACHED` ([les 5](site:fullstack/docs/online/docker/image)), en is het in een paar seconden klaar.

Kijk daarna of het gelukt is:

```bash
docker compose ps
docker compose logs --tail 20
```

Staat er `Up` bij de status en geen traceback in het logboek, open dan je site.

## Draait hij echt?

`Up` betekent alleen dat het programma in de container draait. Of je site ook antwoordt, weet Docker niet. Een site die bij elk verzoek een 500 geeft, staat ook op `Up`. Met een **healthcheck** vraagt Docker zelf elke dertig seconden je site op. Zet hem in WSL in `compose.yaml`, bij je site, onder `labels`:

```yaml
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/')"]
      interval: 30s
      start_period: 30s
      start_interval: 2s
```

`test` is het commando dat Docker in de container draait: een regel Python die je homepage opvraagt. Geeft die een fout of geen antwoord, dan is de test mislukt. In het image staat geen `curl`, maar wel Python. `interval` is hoe vaak Docker kijkt, en in de eerste dertig seconden (`start_period`) kijkt hij elke twee seconden (`start_interval`).

Commit en push, en zet de nieuwe versie op de server met de twee stappen. Nu staat er meer bij de status:

```text
NAME                      STATUS
gastenboek-gastenboek-1   Up 14 seconds (healthy)
```

`healthy` betekent: de laatste test lukte. Traefik let erop: een container die nog niet gezond is, krijgt geen bezoekers. Vlak na een nieuwe versie geeft je site daarom twee of drie seconden `404 page not found`, tot de eerste test lukt. In het logboek zie je de test ook, elke dertig seconden een `GET /` van `127.0.0.1`.

## Werk nooit op de server zelf

Pas je code nooit aan op de server, ook niet "even snel" met nano. De volgende `git pull` weigert dan, of jouw wijziging staat nergens anders en is bij een nieuwe server weg. De server krijgt alleen code die eerst op GitHub stond.

Een paar bestanden horen niet bij je project maar bij de server zelf: `.env` met je domeinnaam, en de map `~/traefik` met de voordeur. Die maak en verander je wel op de server, en ze staan nergens anders. Daarom gaan ze mee in de back-up van [les 16](site:fullstack/docs/online/server/backup).

## Er gaat iets mis

### Your local changes would be overwritten

```text
error: Your local changes to the following files would be overwritten by merge:
        main.py
```

**Oorzaak:** iemand heeft `main.py` op de server veranderd.

**Oplossing:** zet de wijziging, als je hem wilt houden, eerst op je laptop en in git. Gooi hem daarna op de server weg, en haal opnieuw op:

```bash
git checkout -- main.py
git pull
```

### De site start niet meer na de nieuwe versie

`docker compose ps` toont `Restarting`, of de container staat er niet bij.

**Oorzaak:** er zit een fout in de nieuwe code, of een package ontbreekt in `requirements.txt` (`ModuleNotFoundError` in het logboek).

**Oplossing:** lees de fout in `docker compose logs --tail 50`. Moet je site snel weer werken, ga dan terug naar de vorige versie en los het daarna op je laptop op:

```bash
git checkout HEAD~1
docker compose up -d --build
```

`HEAD~1` is de commit vóór de laatste. Als je fix op GitHub staat, ga je terug naar de nieuwste versie, en doe je daarna weer de twee stappen:

```bash
git checkout main
```

### unhealthy

`docker compose ps` toont `(unhealthy)`, en Traefik geeft voor je hele site `404 page not found`.

**Oorzaak:** de healthcheck mislukt. Je homepage geeft een fout, of je site antwoordt niet op poort 8000. Traefik stuurt geen bezoekers naar een container die niet gezond is.

**Oplossing:** open de homepage in de container zelf, en lees de fout:

```bash
docker compose exec gastenboek python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/')"
```

Krijg je een traceback met `HTTP Error 500`, kijk dan in `docker compose logs` welke fout je site gaf. Ga zo nodig terug naar de vorige versie, zoals hierboven.

## Opdrachten

### Opdracht 1: Run - Een nieuwe versie

Zet de healthcheck in je `compose.yaml`, verander een tekst op je homepage, commit en push, en zet de nieuwe versie op je server. Kijk direct na `docker compose up` een paar keer met `docker compose ps`.

<details>
<summary>Antwoord</summary>

Op je laptop: `git add`, `git commit` en `git push`. Op de server de twee stappen van boven. Eerst staat er `(health: starting)`, na een paar seconden `(healthy)`. Daarna zie je de nieuwe tekst, met de oude berichten eronder.

</details>

### Opdracht 2: Make - Een script voor het uitrollen

Zet de stappen in een script `~/uitrollen.sh` op de server, zodat `bash ~/uitrollen.sh` alles doet. Laat het script stoppen zodra een stap misgaat, en laat het aan het eind zien wat er draait.

<details>
<summary>Tip</summary>

Een script is een tekstbestand met op elke regel een commando, dat je met nano maakt. Met de regel `set -e` bovenaan stopt bash bij het eerste commando dat misgaat.

</details>

<details>
<summary>Antwoord</summary>

```bash
set -e
cd ~/gastenboek
git pull
docker compose up -d --build
docker compose ps
```

Zonder `set -e` bouwt het script ook als `git pull` faalde. Dat gaat meestal goed, maar dan denk je dat er een nieuwe versie staat terwijl het de oude is. Je kunt er `docker image prune -f` onder zetten: `-f` slaat de vraag over.

</details>
