# Online zetten: een nieuwe versie uitrollen

<Voorkennis items={[{site: 'editor', to: '/git/pull-clone/stap-2-pull', label: 'Nieuwe commits ophalen met git pull'}]} />

Je site staat online. Nu verander je iets, bijvoorbeeld de `secure=True` uit de vorige les. Je werkt zoals altijd in Ubuntu op je laptop: veranderen, testen met `docker compose up -d --build`, en een commit naar GitHub. Daarna haalt de server de nieuwe versie op.

## Twee stappen op de server

```bash
cd ~/gastenboek
git pull
docker compose up -d --build
```

- `git pull` haalt de nieuwe commits op.
- `docker compose up -d --build` bouwt een nieuw image en vervangt de container. Kwam er niets bij in `requirements.txt`, dan staat de pip-stap er als `CACHED` ([les 5](site:fullstack/docs/online/docker/image)), en is het in een paar seconden klaar.

Kijk daarna of het gelukt is:

```bash
docker compose ps
docker compose logs --tail 20
```

Staat er `Up` bij de status en geen traceback in het logboek, open dan je site.

## Werk nooit op de server zelf

Pas je code nooit aan op de server, ook niet "even snel" met nano. De volgende `git pull` weigert dan, of jouw wijziging staat nergens anders en is bij een nieuwe server weg. De server krijgt alleen code die eerst op GitHub stond. Alleen `.env` maak je op de server, want die hoort bij de server.

## Een back-up

Het volume is het enige op je server dat je niet opnieuw kunt maken. Een kapotte schijf, een `docker compose down -v` of een opgezegde server, en het is weg. Maak er daarom een kopie van, op een andere computer.

Stop je site even, zodat er tijdens het kopiëren niets verandert, en kopieer de map `data` uit de container:

```bash
cd ~/gastenboek
docker compose stop
docker compose cp gastenboek:/app/data ~/backup
docker compose start
```

`docker compose cp` kopieert tussen een container en de server, ook als de container gestopt is. `gastenboek:` is de naam van de service uit `compose.yaml`. Haal de kopie daarna in WSL naar je laptop met `scp`:

```bash
scp -r sam@gastenboek.voorbeeld.nl:backup ~/backup-gastenboek
```

Ging ssh tot nu toe met het IP-adres, dan vraagt hij bij de domeinnaam nog één keer of je de vingerafdruk vertrouwt; het is dezelfde server. Gooi de kopie op de server daarna weg met `rm -r ~/backup`. In `gebruikers.db` staan de wachtwoorden van je bezoekers, als hash; bewaar de back-up dus net zo zorgvuldig als de server zelf.

## Oude images opruimen

Bij elke `--build` blijft het vorige image staan, zonder naam. Na een paar maanden staan er tientallen, van elk honderden megabytes. Kijk hoeveel ruimte Docker gebruikt:

```bash
docker system df
```

Bij `Images` staat onder `RECLAIMABLE` wat er weg kan. Gooi de images zonder naam weg:

```bash
docker image prune
```

```text
WARNING! This will remove all dangling images.
Are you sure you want to continue? [y/N]
```

Typ `y`. *Dangling* betekent: een image zonder naam, waar geen container meer van draait. Je site en Traefik blijven staan.

## Er gaat iets mis

### Your local changes would be overwritten

```text
error: Your local changes to the following files would be overwritten by merge:
        main.py
```

**Oorzaak:** iemand heeft `main.py` op de server veranderd.

**Oplossing:** zet de wijziging, als je hem wilt houden, eerst op je laptop en in git. Gooi hem daarna op de server weg, en haal opnieuw op:

```bash
git checkout -- main.py
git pull
```

### De site start niet meer na de nieuwe versie

`docker compose ps` toont `Restarting`, of de container staat er niet bij.

**Oorzaak:** er zit een fout in de nieuwe code, of een package ontbreekt in `requirements.txt` (`ModuleNotFoundError` in het logboek).

**Oplossing:** lees de fout in `docker compose logs --tail 50`. Moet je site snel weer werken, ga dan terug naar de vorige versie en los het daarna op je laptop op:

```bash
git checkout HEAD~1
docker compose up -d --build
```

`HEAD~1` is de commit vóór de laatste. Als je fix op GitHub staat, ga je terug naar de nieuwste versie, en doe je daarna weer de twee stappen:

```bash
git checkout main
```

### no space left on device

**Oorzaak:** de schijf van je server is vol, meestal door oude images.

**Oplossing:** kijk met `docker system df` waar de ruimte zit, en ruim op met `docker image prune`. Typ nooit `docker volume prune` of `docker system prune --volumes` op een server: die gooien ook volumes weg waar op dat moment geen container aan hangt.

## Opdrachten

### Opdracht 1: Run - Een nieuwe versie

Verander een tekst op je homepage, commit en push, en zet de nieuwe versie op je server. Maak daarna een back-up, en haal hem naar je laptop.

<details>
<summary>Antwoord</summary>

Op je laptop: `git add`, `git commit` en `git push`. Op de server de twee stappen van boven, en daarna de stappen van **Een back-up**. Na de nieuwe versie zie je de nieuwe tekst, met de oude berichten eronder. In `~/backup-gastenboek` op je laptop staan je databases.

</details>

### Opdracht 2: Make - Een script voor het uitrollen

Zet de stappen in een script `~/uitrollen.sh` op de server, zodat `bash ~/uitrollen.sh` alles doet. Laat het script stoppen zodra een stap misgaat, en laat het aan het eind zien wat er draait.

<details>
<summary>Tip</summary>

Een script is een tekstbestand met op elke regel een commando, dat je met nano maakt. Met de regel `set -e` bovenaan stopt bash bij het eerste commando dat misgaat.

</details>

<details>
<summary>Antwoord</summary>

```bash
set -e
cd ~/gastenboek
git pull
docker compose up -d --build
docker compose ps
```

Zonder `set -e` bouwt het script ook als `git pull` faalde. Dat gaat meestal goed, maar dan denk je dat er een nieuwe versie staat terwijl het de oude is. Je kunt er `docker image prune -f` onder zetten: `-f` slaat de vraag over.

</details>

Je site staat online, in een container die niet als `root` draait, met de berichten in een volume, achter een voordeur met HTTPS, en met alleen de deuren open die hij nodig heeft. Wil je je containers in de browser beheren, dan is er nog een extra les.
