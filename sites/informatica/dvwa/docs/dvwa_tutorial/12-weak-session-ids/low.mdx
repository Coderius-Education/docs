# Weak Session IDs — Low

<LabBadge status="deels" />

<Ethiek />

Wanneer je inlogt op een website, krijg je van de webserver een uniek bewijs (een "Sessie ID") opgeslagen in een cookie. Maar wat als de server dat bewijs op een voorspelbare manier aanmaakt?

<Voorkennis
  items={[
    {to: '/docs/http_leren', label: 'Cookies en sessies'},
  ]}
/>

## 1. Predict (Voorspel)

De server gebruikt de volgende code om bij elke klik een nieuw sessie-ID te genereren:

```php
if (!isset ($_SESSION['last_session_id'])) {
    $_SESSION['last_session_id'] = 0;
}
$_SESSION['last_session_id']++; // Verhoog de teller met 1

$cookie_value = $_SESSION['last_session_id'];
setcookie("dvwaSession", $cookie_value);
```

**Vraag:** Waarom is het een verschrikkelijk slecht idee om een sessie-ID simpelweg een oplopend getal (1, 2, 3...) te maken?

<details>

<summary>Antwoord</summary>

Als jouw cookie-waarde `dvwaSession=12` is, heeft de vorige persoon waarschijnlijk sessie `11` en de volgende krijgt `13`. Een hacker past de waarde in zijn eigen cookie aan naar `11`, vernieuwt de pagina en de server ziet hem als die andere persoon die op dat moment was ingelogd. Dit is **Session Hijacking**.

</details>

## 2. Run (Uitvoeren)

Start het lab en genereer een paar sessie-IDs.

<DvwaLab module="weak_session_ids" level="low" />

> **Labbeperking:** Het aanpassen van cookies via F12 werkt beperkt in het embedded lab. Je kunt de gegenereerde waarden wél observeren, maar voor het daadwerkelijk kapen van een sessie heb je een [lokale DVWA-installatie](/docs/dvwa_installatie) nodig.

Klik een paar keer op de knop om een nieuwe sessie op te vragen. Noteer de waarden die worden getoond.

## 3. Investigate (Onderzoeken)

Bekijk de sessie-ID die het lab bij elke klik toont, en de regel eronder die de vorige en volgende waarde verklapt.

**Vraag:** Wat is het patroon in de opeenvolgende waarden? Wat onthult dit over hoe gemakkelijk het is om een andere gebruikerssessie te raden?

<details>

<summary>Antwoord</summary>

De waarden stijgen telkens met 1: `1`, `2`, `3`, ... Het patroon is volledig voorspelbaar. Een aanvaller hoeft alleen te weten dat een slachtoffer is ingelogd en de waarde te raden (of simpelweg alle getallen in de buurt te proberen). Er is geen willekeur, geen geheimhouding.

</details>

## 4. Modify & Make (Aanpassen & Maken)

Je weet nu dat de sessie-ID's oplopen. De volgende stap — een andere sessie overnemen — doe je op een echte DVWA, waar de ID in een aanpasbare cookie zit (in dit lab zie je de waarde alleen ter observatie).

<details>

<summary>Tip</summary>

Op een echte DVWA ga je in Developer Tools naar **Application** → **Cookies** → `http://localhost` en dubbelklik je op de waarde van `dvwaSession`.

</details>

<details>

<summary>Antwoord</summary>

Op een echte DVWA:

1. Ga naar **Application** → **Cookies**.
2. Zoek de cookie `dvwaSession`.
3. Verander de waarde naar `1` of `2`.
4. Vernieuw de pagina. De server beschouwt je nu als de gebruiker met dat sessie-ID.

</details>

## 5. ✓ Wat moest je zien?

:::tip[Controle]
- De getoonde waarden zijn aantoonbaar oplopend (1, 2, 3...) — geen willekeur.
- Op een echte DVWA verander je met een ander getal van gebruikerssessie.
- De server controleert niet of het gebruikte sessie-ID bij jou hoort.

De sessie-aanpassing zelf doe je in een lokale DVWA-installatie waar je volledige toegang hebt tot cookies.
:::

## 6. Er gaat iets mis...

Je past je cookie aan naar ID `999` en de server logt je uit. Dit komt omdat gebruiker 999 niet actief is ingelogd — de server vindt geen overeenkomst in zijn sessie-tabel en vernietigt de verbinding. Session Hijacking werkt alleen op **actieve** sessies die op dat moment op de server geregistreerd staan.
