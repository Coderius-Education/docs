# Docentenhandleiding

Praktische informatie voor docenten die deze cursus klassikaal willen inzetten: wat de site is, welke randvoorwaarden er zijn, en hoe je de lessen indeelt.

## Wat is dit?

Een interactieve cursus **fullstack-ontwikkeling met FastAPI**: je leerlingen voegen een Python-back-end toe aan een website. Doelgroep: leerlingen die al wat Python, HTML en JavaScript kennen en willen leren hoe front-end en back-end samenwerken.

Per onderwerp staat er een minimale, werkende handler die je daarna uitbreidt met validatie, templates en een database. De nadruk ligt op het samenspel tussen verzoek (browser) en antwoord (server).

:::note[Voorkennis]
Deze cursus bouwt voort op Python en op HTML, CSS en JavaScript. Plan die eerst in als je leerlingen daar nog niet mee bekend zijn. Op het [cursusoverzicht](/cursussen) staat welke cursus waarop voortbouwt.

In de lessen zelf staat de voorkennis per les in een dichtgeklapt blok, zodat een leerling die vastloopt op een `def` of een `<form>` terug kan naar de uitleg zonder dat de les daarmee begint.
:::

## Technische randvoorwaarden

| Wat | Antwoord |
|---|---|
| Operating system | Windows, macOS of Linux |
| Oefenen | Veel voorbeelden draaien in de browser |
| Eigen project | Python 3 en een editor (VS Code) lokaal aanbevolen; wie wil kan er <SiteLink site="editor" to="/git/">git</SiteLink> naast gebruiken |
| Account | Niet nodig |
| Internet | Vereist — de site is online |

## Didactische aanpak (PRIMM)

Elke les volgt hetzelfde vaste patroon — de **PRIMM-methode** — afgesloten met een troubleshooting-sectie:

1. **Predict** — je leerling voorspelt wat een endpoint of stuk code doet.
2. **Run** — je leerling draait het en controleert die voorspelling.
3. **Investigate** — kleine experimenten met het verzoek of het antwoord.
4. **Modify** — een opdracht die voortbouwt op de bestaande handler.
5. **Make** — een vrijere opdracht waarin je leerling zelf een endpoint bouwt.
6. **Er gaat iets mis** — veelvoorkomende fouten, met oorzaak en oplossing.

Tips en antwoorden staan in `<details>`-blokken. Laat je leerlingen eerst zelf proberen voordat ze openklikken.

## Klassikaal gebruik & differentiatie

- **Plenair starten**: bespreek de Predict-vraag klassikaal, daarna werken je leerlingen zelfstandig door.
- **Snelle leerlingen** breiden een endpoint uit met extra validatie of een tweede route.
- **Langzamere leerlingen** mogen de Make-opdracht overslaan zonder dat de volgende les daarop bouwt.
- **Beoordelen**: de cursus heeft geen vaste eindopdracht. Het gastenboek dat je leerlingen in de basis bouwen, of een eigen project op dezelfde manier, kunnen ze uploaden op [Project checken](/project-checken). Die nakijker laat zien welke onderwerpen erin terugkomen; hij is bedoeld als checklist, niet als cijfer.

## Leerlijn

De lessen staan in de **FastAPI**-sidebar en bouwen op elkaar voort. Die begint met een [startpagina](/docs/FastAPI): wat je leerlingen aan het eind hebben (een nagebouwd plaatje van het gastenboek), de voorkennis uit de andere cursussen, en de route als kaart met per blok een zin en de lessen. Daarna komt [Installatie](/docs/FastAPI/installatie); de [Cheatsheet](/docs/cheatsheet) en [Er gaat iets mis](/docs/troubleshooting) zijn naslag en staan in de navbar. [Projectstructuur](/docs/FastAPI/projectstructuur), met de mappen van het project per les, staat bovenaan de cheatsheet.

De sidebar heeft twee delen. De **basis** (Je eerste server, HTML-pagina's, Templates en formulieren, Gegevens opslaan en tonen) eindigt met een werkend gastenboek: een formulier, opslaan, een overzicht, een detailpagina en een nette 404. Wat volgt zijn drie **uitbreidingen** (htmx, JavaScript, cookies en sessies) en een afronding. Die maken het gastenboek mooier, maar zijn niet nodig om het te laten werken. Heb je weinig tijd, dan kun je na de basis stoppen; wie verder gaat, volgt de uitbreidingen op volgorde, want "Server of browser?" vergelijkt de server met htmx en JavaScript.

Vijf keer onderweg staat een diagram van de hele keten, browser links en server rechts, met per stap een link naar de les. Het begint kaal [bij het eerste verzoek](/docs/FastAPI/verzoek-eerste), direct na het eerste endpoint, en groeit mee. [Bij één pagina](/docs/FastAPI/verzoek-static), aan het eind van HTML-pagina's, komen de losse verzoeken voor CSS en afbeeldingen erbij. [Bij klikken en versturen](/docs/FastAPI/verzoek-get), aan het eind van Gegevens opslaan en tonen, de database en de template, en bij een formulier de omleiding. [Zonder herladen](/docs/FastAPI/verzoek-htmx), aan het eind van de htmx-uitbreiding, wordt die omleiding een stuk HTML als antwoord; [bij een sessie](/docs/FastAPI/verzoek-sessie), aan het eind van Onthouden, komt de cookie erbij. [Hoe een verzoek werkt](/docs/FastAPI/hoe-een-verzoek-werkt) bundelt ze bij het afronden met een tabel "waar hoort jouw code".

| Onderwerp | Leerdoel |
|---|---|
| Je eerste endpoint | Een API-route maken en aanroepen |
| Kijken wat de browser doet | Het tabblad Netwerk: verzoek, antwoord en statuscode |
| HTML tonen en HTML in bestanden | Pagina's serveren vanuit Python en uit bestanden |
| CSS in een eigen bestand (static files) | Eén stylesheet voor alle pagina's, en de cache |
| Templates met Jinja2 | Een pagina met waarden uit Python: `{{ }}`, het dictionary, en wat de browser krijgt |
| GET vs POST en formulieren | Gebruikersinvoer verwerken en beantwoorden met een template |
| Gegevens opslaan met SqliteDict | Gegevens opslaan en ophalen met SQLite |
| Een formulier opslaan | Het gastenboek: elk bericht een eigen sleutel |
| Alles tonen: een for-lus in je template | Opgeslagen records op een pagina zetten met een for-lus |
| Doorsturen na opslaan (redirect) | Doorsturen na een POST (post/redirect/get), en verwijderen |
| Eén item tonen: path-parameters en 404 | Path-parameters en zelf een 404 sturen |
| Zonder herladen met htmx *(uitbreiding)* | Een knop die iets aan de server vraagt terwijl de pagina blijft staan |
| htmx-recepten *(uitbreiding)* | Overzicht van recepten: formulier, verversen, vanzelf verversen, verwijderen, zoeken |
| JavaScript erbij *(uitbreiding)* | Code die in de browser draait in plaats van op de server |
| Console en Elementen *(uitbreiding)* | Uitvoer en fouten van JavaScript zien, en de pagina zoals de browser hem nu heeft |
| Server of browser? *(uitbreiding)* | Kiezen waar iets hoort, en waarom controles op de server moeten |
| Onthouden met een cookie *(uitbreiding)* | De browser iets laten onthouden tussen twee verzoeken |
| Onthouden op de server: sessies *(uitbreiding)* | Alleen een sessie-id bij de bezoeker, de gegevens op de server |
| Cookie of sessie? *(uitbreiding)* | Kiezen tussen de twee, en waarom je niet alles kunt geloven |
| Laat het aan anderen zien | De server openzetten voor het netwerk |

"Een formulier opslaan" tot en met "Eén item tonen" bouwen samen het gastenboek. Alles wat een latere les nodig heeft, staat in de hoofdtekst en niet in een opdracht: het gastenboek zelf in "Een formulier opslaan", het verwijderen in "Doorsturen na opslaan". Daarna hebben je leerlingen een werkende webapplicatie met een overzicht, een detailpagina en nette foutafhandeling.

De ontwikkelaarstools van de browser krijgen twee eigen lessen, zonder schermafbeeldingen: de lessen bouwen het paneel na met de Nederlandse en Engelse naam van elk tabblad naast elkaar. "Kijken wat de browser doet" komt direct na het eerste endpoint en leert het tabblad Netwerk: één verzoek en de statuscode. De cache, de reden waarom een wijziging niet doorkomt en de vraag die je in de les het vaakst krijgt, komt bij "CSS in een eigen bestand", waar hij voor het eerst speelt. "Console en Elementen" komt na "JavaScript erbij", als de terminal niets meer laat zien, en bereidt "Server of browser?" voor: wie in Elementen `maxlength` weghaalt, ziet daar wat de bezoeker kan.

Na de basis komt de eerste uitbreiding, "Zonder herladen (htmx)": de server doet het werk, maar de pagina blijft staan, omdat htmx het verzoek stuurt en het antwoord op zijn plek zet. De eerste les is bewust zo klein mogelijk: één knop met twee attributen die de tijd van de server ophaalt, en een endpoint van drie regels. Daarna volgt één les met een overzicht van recepten (formulier, verversen, vanzelf verversen, verwijderen, zoeken), waaruit je leerlingen kiezen wat hun gastenboek nodig heeft. Ze schrijven er geen JavaScript voor; ze hergebruiken alles wat ze al hebben. Elk endpoint geeft een stukje HTML terug in plaats van een omleiding, en dat is ook de fout die je het meest zult zien: een hele pagina in het doel. De tweede valkuil is dat htmx een mislukt verzoek stil negeert; de lessen sturen daarom steeds naar het tabblad Netwerk. Het bestand `htmx.min.js` staat op deze site om te downloaden, zodat het ook werkt op een netwerk dat externe scripts blokkeert.

Vanaf "JavaScript erbij" komt de browserkant in beeld. Je leerlingen kennen JavaScript al uit de web-cursus; nieuw is de vraag wáár code hoort. Die vraag krijgt een eigen les ("Server of browser?") nadat ze de drie smaken hebben gevoeld: een formulier versturen gaat via de server en de pagina verspringt, met htmx blijft de pagina staan, en een tekenteller draait in de browser zonder dat de server er iets van ziet. De tabel in die les heeft voor elk een kolom.

Daarop volgt "Onthouden", drie lessen die het sterkst zijn als je ze achter elkaar plant. In de eerste veranderen je leerlingen hun eigen cookie in een andere naam en zien ze de server dat klakkeloos overnemen. In de tweede lossen ze dat op door alleen een sessie-id bij de bezoeker te laten en de gegevens op de server te zetten. Het is voor veel leerlingen het eerste moment waarop beveiliging concreet wordt: de verwijderknop verbergen is niet hetzelfde als verwijderen onmogelijk maken.

"Cookie of sessie?" sluit dat blok af zoals "Server of browser?" het vorige afsluit — niet met nieuwe techniek, maar met de vraag wanneer je wat kiest. De kern is dat een sessie ook gewoon een cookie is; het verschil zit in wát erin staat. Leerlingen die alles voor de zekerheid een sessie willen maken, vinden daar het tegenargument: een voorkeur die niemand kan schaden hoort in een gewone cookie.

Daarna sluit de cursus af met een overzicht van alle diagrammen en de server openzetten voor het netwerk, zodat de klas elkaars project kan bezoeken.

Wat hier bewust níét in zit, is `fetch`: JavaScript dat zelf data ophaalt bij een endpoint. Dat vraagt `async`/`await`, JSON verwerken en objecten — stof die de web-cursus nog niet behandelt. Het blok "Zonder herladen" vult dat gat met htmx: de server stuurt HTML, niet JSON. Leerlingen die toch `fetch` willen kun je die kant op sturen; de cursus bouwt er niet op.

### De reeks Veiligheid

Naast de FastAPI-sidebar staat een tweede sidebar, **Veiligheid**. De meeste reeksen passen na de hele FastAPI-route, dus ook na de drie uitbreidingen: ze bouwen op formulieren, templates, htmx, sessies en `HTTPException`, en je leerlingen hebben dan een eigen gastenboek om te beschermen. Invoer kan al direct na de basis; de verwijzingen naar Server of browser? zijn daar optioneel. Elke reeks werkt in een eigen map met een eigen virtual environment, zodat het gastenboek van de leerling heel blijft; hoe dat gaat staat in [Een map per reeks](/docs/veiligheid/gereedschap#een-map-per-reeks). De route begint met een [startpagina](/docs/veiligheid) (het ene idee, de spelregel, een kaart en een overzicht van statuscodes) en een les [Een script als bezoeker](/docs/veiligheid/gereedschap), waarin ze met `httpx` verzoeken sturen zonder browser. Daarna volgen de reeksen, van dichtbij het eigen gastenboek naar ver weg. Elke reeks gaat van de zwakheid die de leerling zelf nadoet, via de oplossing in FastAPI, naar wat er in de praktijk nog gebeurt, inclusief wat de wet zegt. De reeksen zijn los te volgen; alleen Cookies bouwt op de server uit Wie mag wat.

De reeks is opzettelijk defensief. Elke zelftest draait tegen de eigen server op `127.0.0.1` en de eigen database; er staat een `:::danger`-blok boven dat zegt dat het aanvallen van een ander strafbaar is. De demonstratie van een zwakheid is klein: twintig verzoeken, de eigen database bekijken, een vet woord in het gastenboek, de eigen cookie in de Console. Er staat geen script in dat wachtwoorden raadt of een server platlegt. Waarom een snelle hash zwak is, laat de wachtwoordenreeks zien met een meting van de rekentijd.

| Reeks, in volgorde | Zwakheid | Kern van de oplossing |
|---|---|---|
| Invoer controleren | `maxlength` houdt een script niet tegen | de grens in `Form` op de server |
| HTML van een bezoeker (XSS) | ingevulde HTML draait in andermans browser | escapen bij de uitvoer |
| Wie mag wat | een verborgen knop is geen slot | de controle op de server, met `403` |
| Cookies afschermen | een script leest het sessie-id | `httponly`, `samesite`, `secure` |
| Wachtwoorden veilig opslaan | een lek geeft alle wachtwoorden weg | hashen met Argon2, in acht kleine lessen |
| Te veel verzoeken (DoS) | veel verzoeken leggen de server plat | een verzoeklimiet met `slowapi` |

De beloofde uitvoer en foutmeldingen in deze reeks draaien niet mee in CI, die alleen de Python-syntax controleert. Ze zijn met de hand nagedraaid tegen een echte server. Werk je een les bij, controleer een gewijzigde uitvoer dan zelf in een virtual environment met de echte packages.
