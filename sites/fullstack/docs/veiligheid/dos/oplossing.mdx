# Te veel verzoeken: de oplossing

In [de zwakheid](./zwakheid) zag je dat je server elk verzoek beantwoordt, hoe
vaak het ook komt. Je kunt niet voorkomen dat iemand veel verzoeken *stuurt*.
Wat je wél kunt, is weigeren om ze allemaal te *beantwoorden*. Krijgt één
bezoeker meer dan een paar verzoeken per minuut, dan is dat geen mens die een
pagina leest, maar een script. Zulke verzoeken sla je over.

Dat heet een **rate limit**, een verzoeklimiet.

## Een limiet met `slowapi`

De module `slowapi` regelt de limiet voor je. Installeer hem met
`python -m pip install slowapi`.

<CodeUitleg>

```python showLineNumbers
from fastapi import FastAPI, Request
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.util import get_remote_address
from slowapi.errors import RateLimitExceeded

limiter = Limiter(key_func=get_remote_address)

app = FastAPI()
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)

@app.get("/")
@limiter.limit("5/minute")
async def root(request: Request):
    return {"bericht": "Hallo wereld!"}
```

<Regel n={6}>
De `Limiter` houdt bij hoeveel verzoeken er binnenkomen. `get_remote_address` zegt: tel per computer, aan de hand van zijn adres.
</Regel>

<Regel n={9} tot={10}>
Je hangt de limiter aan je app, en zegt wat er moet gebeuren als de grens bereikt is: het antwoord `429 Too Many Requests`.
</Regel>

<Regel n={13}>
`@limiter.limit("5/minute")` boven een endpoint betekent: hoogstens vijf verzoeken per minuut per computer. Het zesde krijgt `429`.
</Regel>

<Regel n={14}>
Door de limiter heeft de functie nu `request: Request` nodig. Zonder die parameter weet `slowapi` niet welk verzoek hij bekijkt.
</Regel>

</CodeUitleg>

## Doe de test opnieuw

Start je server opnieuw en draai `test_verzoeken.py` uit
[stap 1](./zwakheid) nog een keer. Nu zie je iets anders:

```
Verzoek 1: status 200
Verzoek 2: status 200
Verzoek 3: status 200
Verzoek 4: status 200
Verzoek 5: status 200
Verzoek 6: status 429
Verzoek 7: status 429
```

De eerste vijf verzoeken krijgen antwoord, en je server weigert de rest met
`429`. Aan het eind staat `Gelukt: 5 van de 20`. Je server doet nog maar vijf
keer moeite, hoeveel het script ook stuurt. Een echte bezoeker die één keer je
pagina opvraagt, merkt er niets van.

Zo stopt een limiet een DoS van één computer. Tegen een DDoS van duizenden
computers helpt een limiet per computer minder, want elk apparaat blijft onder
de grens. Wat daar in de praktijk tegen gebeurt, zie je in
[stap 3](./praktijk).

## Er gaat iets mis

Je server start niet, en in de terminal eindigt de foutmelding met:

```
Exception: No "request" or "websocket" argument on function "<function root at 0x…>"
```

**Oorzaak:** je endpoint heeft geen `request: Request` als parameter, terwijl
`@limiter.limit(...)` erboven staat. `slowapi` controleert dat al bij het
starten: zonder `request` weet hij niet van wie een verzoek komt, dus kan hij
niet tellen. Het getal achter `0x` verschilt per keer.

**Oplossing:** zet `request: Request` tussen de haakjes van je functie:

```python
# FOUT
@app.get("/")
@limiter.limit("5/minute")
async def root():
    return {"bericht": "Hallo wereld!"}

# GOED
@app.get("/")
@limiter.limit("5/minute")
async def root(request: Request):
    return {"bericht": "Hallo wereld!"}
```

## Opdrachten

### Opdracht 1: Predict - Wat zie je?

Je hebt deze limiet op je endpoint gezet:

```python
@app.get("/tijd")
@limiter.limit("3/minute")
async def tijd(request: Request):
    return {"bericht": "Het is nu laat"}
```

Je vraagt `/tijd` vier keer snel achter elkaar op.

**Vraag:** welke statuscodes krijg je terug?

<details>
<summary>Tip</summary>

De limiet is drie per minuut. Tel hoeveel verzoeken er antwoord krijgen
voordat de grens bereikt is.

</details>

<details>
<summary>Antwoord</summary>

```
200
200
200
429
```

De eerste drie passen binnen de limiet, het vierde weigert de server met `429
Too Many Requests`.

</details>

### Opdracht 2: Run

Zet een limiet van `10/minute` op je startpagina. Pas `test_verzoeken.py` niet
aan (die stuurt nog twintig verzoeken), start je server en draai het script.
Tel hoeveel verzoeken `200` krijgen en hoeveel `429`.

<details>
<summary>Antwoord</summary>

Tien verzoeken krijgen `200`, de andere tien `429`. Aan het eind staat er
`Gelukt: 10 van de 20`.

</details>

### Opdracht 3: Investigate - Een strengere grens

Verander de limiet in `"2/minute"` en draai het script opnieuw. Wat gebeurt
er, en waarom zou een limiet van twee per minuut op een echte site geen goed
idee zijn?

<details>
<summary>Tip</summary>

Denk aan een bezoeker die na het lezen van je startpagina op een link klikt
en terugkomt.

</details>

<details>
<summary>Antwoord</summary>

Nu krijgen maar twee verzoeken `200` en de rest `429`. Op een echte site is
dat te streng: een gewone bezoeker die een paar pagina's bekijkt of even
terugklikt, zit zo aan twee verzoeken, en dan weigert je server hem zelf. Een
limiet moet hoog genoeg zijn voor een mens, en laag genoeg om een script te
stoppen.

</details>

### Opdracht 4: Make - Bescherm een tweede endpoint (uitdaging)

Voeg een endpoint `/zoeken` toe met een limiet die past bij zoeken: een mens
zoekt af en toe, een script vuurt honderden zoekopdrachten af. Kies zelf een
grens en leg in één zin uit waarom.

<details>
<summary>Antwoord</summary>

```python
@app.get("/zoeken")
@limiter.limit("20/minute")
async def zoeken(request: Request):
    return {"bericht": "Zoekresultaten"}
```

Twintig per minuut laat ruimte voor een bezoeker die meerdere keren zoekt,
maar stopt een script dat er honderden per minuut wil doen. Elke grens tussen
ongeveer tien en dertig is verdedigbaar, zolang je hem kunt uitleggen.

</details>
