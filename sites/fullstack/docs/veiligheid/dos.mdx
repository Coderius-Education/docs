Je hebt een endpoint gemaakt dat op een `GET`-verzoek reageert:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
async def root():
    return {"bericht": "Hallo wereld!"}
```

Eén bezoeker vraagt de pagina op, je server antwoordt, klaar. Maar wat gebeurt
er als iemand niet één keer vraagt, maar tienduizend keer per seconde? Je
server probeert elk verzoek te beantwoorden. Op een gegeven moment is de
computer bezig met alleen nog die verzoeken, en krijgt een echte bezoeker geen
antwoord meer. De site ligt plat.

Dat is een **DoS**-aanval: *Denial of Service*, oftewel "dienst weigeren". Niet
door in te breken, maar door de server zo druk te maken dat hij niets nuttigs
meer doet.

## DoS en DDoS

Eén computer die verzoeken afvuurt, houdt een server zelden plat: jouw laptop
verstuurt ze niet sneller dan de server ze afhandelt. Daarom komen echte
aanvallen van heel veel computers tegelijk. Dat heet **DDoS**: *Distributed
Denial of Service*, "verspreid" over duizenden machines.

Die machines zijn meestal niet van de aanvaller zelf. Het zijn gekaapte
computers, camera's en routers, samen een **botnet**. De eigenaren weten
vaak niet eens dat hun apparaat meedoet.

| | DoS | DDoS |
|:---:|:---:|:---:|
| Waar komen de verzoeken vandaan | één computer | heel veel computers |
| De D staat voor | Denial | Distributed |
| Tegen te houden met een blokkade per computer | ja | veel lastiger |

Het idee is bij allebei hetzelfde: de server overspoelen met werk. DDoS is
alleen groter en moeilijker te stoppen, want je kunt niet één boosdoener
blokkeren.

## Doe het na, op je eigen server

Je hoeft niet te geloven dat veel verzoeken een server bezighouden: je kunt het
zelf zien. Klein, en op je eigen computer.

:::danger[Alleen je eigen server]
Doe dit **uitsluitend** tegen je eigen server op `127.0.0.1` (je eigen
computer). Een ander zijn server bestoken met verzoeken is een aanval, en
strafbaar, ook als het "maar een testje" is. `127.0.0.1` is het adres dat altijd
naar je eigen machine wijst en die verlaat het netwerk niet.
:::

Start eerst je server, zoals altijd:

```bash
fastapi dev main.py
```

Maak daarnaast een apart bestand `test_verzoeken.py`. Dit is geen deel van je
server; het is een los scriptje dat de rol van bezoeker speelt. Het vraagt
twintig keer achter elkaar je startpagina op en telt de antwoorden:

<CodeUitleg>

```python showLineNumbers
import httpx

adres = "http://127.0.0.1:8000/"

gelukt = 0
for nummer in range(20):
    antwoord = httpx.get(adres)
    print(f"Verzoek {nummer + 1}: status {antwoord.status_code}")
    if antwoord.status_code == 200:
        gelukt += 1

print(f"Gelukt: {gelukt} van de 20")
```

<Regel n={1}>
`httpx` is een module om verzoeken te versturen, net zoals een browser dat doet. Installeer hem één keer met `python -m pip install httpx`.
</Regel>

<Regel n={3}>
`127.0.0.1` is je eigen computer, en `:8000` is de poort waarop `fastapi dev` draait. Ditzelfde adres typ je anders in de browser.
</Regel>

<Regel n={6} tot={9}>
De for-loop stuurt twintig keer een `GET`-verzoek. `httpx.get` geeft een antwoord terug met een `status_code`: 200 betekent gelukt.
</Regel>

</CodeUitleg>

Draai het script in een tweede terminal:

```bash
python test_verzoeken.py
```

Je ziet twintig keer status 200, en aan het eind `Gelukt: 20 van de 20`. Twintig
verzoeken zijn niets voor je server. Maar zet in gedachten `range(20)` op
`range(20000)`, en laat dat door duizend computers tegelijk doen: dan is dit
precies hoe een DDoS eruitziet, alleen groter.

Er is nu niets dat je server tegen die twintig, of twintigduizend, verzoeken
beschermt. Elk verzoek krijgt antwoord. Dat gaan we veranderen.

## De rem erop: een verzoeklimiet

Je kunt niet voorkomen dat iemand veel verzoeken *stuurt*. Wat je wél kunt, is
weigeren om ze allemaal te *beantwoorden*. Krijgt één bezoeker meer dan een
paar verzoeken per minuut, dan is dat geen mens die een pagina leest, maar een
script. Zulke verzoeken sla je over.

Dat heet een **rate limit**, een verzoeklimiet. De module `slowapi` regelt het
voor je. Installeer hem met `python -m pip install slowapi`.

<CodeUitleg>

```python showLineNumbers
from fastapi import FastAPI, Request
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.util import get_remote_address
from slowapi.errors import RateLimitExceeded

limiter = Limiter(key_func=get_remote_address)

app = FastAPI()
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)

@app.get("/")
@limiter.limit("5/minute")
async def root(request: Request):
    return {"bericht": "Hallo wereld!"}
```

<Regel n={6}>
De `Limiter` houdt bij hoeveel verzoeken er binnenkomen. `get_remote_address` zegt: tel per computer, aan de hand van zijn adres.
</Regel>

<Regel n={9} tot={10}>
Je hangt de limiter aan je app, en zegt wat er moet gebeuren als de grens bereikt is: het antwoord `429 Too Many Requests`.
</Regel>

<Regel n={13}>
`@limiter.limit("5/minute")` boven een endpoint betekent: hoogstens vijf verzoeken per minuut per computer. Het zesde krijgt `429`.
</Regel>

<Regel n={14}>
Door de limiter heeft de functie nu `request: Request` nodig. Zonder die parameter weet `slowapi` niet welk verzoek hij bekijkt.
</Regel>

</CodeUitleg>

## Doe de test opnieuw

Start je server opnieuw en draai `test_verzoeken.py` nog een keer. Nu zie je iets
anders:

```
Verzoek 1: status 200
Verzoek 2: status 200
Verzoek 3: status 200
Verzoek 4: status 200
Verzoek 5: status 200
Verzoek 6: status 429
Verzoek 7: status 429
```

De eerste vijf verzoeken krijgen antwoord, de rest wordt geweigerd met `429`.
Je server doet nog maar vijf keer moeite, hoeveel het script ook stuurt. Een
echte bezoeker die één keer je pagina opvraagt, merkt er niets van.

Zo stopt een limiet een DoS van één computer. Tegen een DDoS van duizenden
computers helpt een limiet per computer minder, want elk apparaat blijft onder
de grens. Daar heb je hulp van buiten voor nodig, bijvoorbeeld van je
hostingpartij; dat valt buiten deze cursus. De limiet hierboven is je eerste
verdediging, en houdt de meeste simpele aanvallen al tegen.

## Er gaat iets mis

```
AttributeError: 'Request' object has no attribute 'app'
```

**Oorzaak:** je endpoint heeft geen `request: Request` als parameter, terwijl
`@limiter.limit(...)` erboven staat. `slowapi` zoekt dan een verzoek dat er niet
is.

**Oplossing:** zet `request: Request` tussen de haakjes van je functie:

```python
# FOUT
@app.get("/")
@limiter.limit("5/minute")
async def root():
    return {"bericht": "Hallo wereld!"}

# GOED
@app.get("/")
@limiter.limit("5/minute")
async def root(request: Request):
    return {"bericht": "Hallo wereld!"}
```

## Opdrachten

### Opdracht 1: Predict - Wat zie je?

Je hebt deze limiet op je endpoint gezet:

```python
@app.get("/tijd")
@limiter.limit("3/minute")
async def tijd(request: Request):
    return {"bericht": "Het is nu laat"}
```

Je vraagt `/tijd` vier keer snel achter elkaar op.

**Vraag:** welke statuscodes krijg je terug?

<details>
<summary>Tip</summary>

De limiet is drie per minuut. Tel hoeveel verzoeken er antwoord krijgen
voordat de grens bereikt is.

</details>

<details>
<summary>Antwoord</summary>

```
200
200
200
429
```

De eerste drie passen binnen de limiet, het vierde wordt geweigerd met `429
Too Many Requests`.

</details>

### Opdracht 2: Run

Zet een limiet van `10/minute` op je startpagina. Pas `test_verzoeken.py` niet
aan (die stuurt nog twintig verzoeken), start je server en draai het script.
Tel hoeveel verzoeken `200` krijgen en hoeveel `429`.

<details>
<summary>Antwoord</summary>

Tien verzoeken krijgen `200`, de andere tien `429`. Aan het eind staat er
`Gelukt: 10 van de 20`.

</details>

### Opdracht 3: Investigate - Een strengere grens

Verander de limiet in `"2/minute"` en draai het script opnieuw. Wat gebeurt
er, en waarom zou een limiet van twee per minuut op een echte site geen goed
idee zijn?

<details>
<summary>Tip</summary>

Denk aan een bezoeker die na het lezen van je startpagina op een link klikt
en terugkomt.

</details>

<details>
<summary>Antwoord</summary>

Nu krijgen maar twee verzoeken `200` en de rest `429`. Op een echte site is
dat te streng: een gewone bezoeker die een paar pagina's bekijkt of even
terugklikt, zit zo aan twee verzoeken en wordt dan zelf geweigerd. Een limiet
moet hoog genoeg zijn voor een mens, en laag genoeg om een script te stoppen.

</details>

### Opdracht 4: Make - Bescherm een tweede endpoint (uitdaging)

Voeg een endpoint `/zoeken` toe met een limiet die past bij zoeken: een mens
zoekt af en toe, een script vuurt honderden zoekopdrachten af. Kies zelf een
grens en leg in één zin uit waarom.

<details>
<summary>Antwoord</summary>

```python
@app.get("/zoeken")
@limiter.limit("20/minute")
async def zoeken(request: Request):
    return {"bericht": "Zoekresultaten"}
```

Twintig per minuut laat ruimte voor een bezoeker die meerdere keren zoekt,
maar stopt een script dat er honderden per minuut wil doen. Elke grens tussen
ongeveer tien en dertig is verdedigbaar, zolang je hem kunt uitleggen.

</details>
