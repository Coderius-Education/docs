# Wachtwoorden: de zwakheid

<Voorkennis
  items={[
    {site: 'python', to: '/docs/data/tuples', label: 'Tuples uitpakken'},
  ]}
/>

Een site met accounts moet wachtwoorden bewaren, anders kan niemand inloggen.
De eerste versie die bijna iedereen schrijft, bewaart het wachtwoord precies
zoals de gebruiker het intypt. Met een [formulier](/docs/FastAPI/forms) en de
[database](/docs/FastAPI/database) uit de FastAPI-lessen ziet dat er zo uit:

<CodeUitleg>

```python showLineNumbers
from fastapi import FastAPI, Form
from sqlitedict import SqliteDict

app = FastAPI()

@app.post("/registreer")
async def registreer(naam: str = Form(...), wachtwoord: str = Form(...)):
    with SqliteDict("gebruikers.db") as db:
        db[naam] = wachtwoord
        db.commit()
    return {"bericht": f"Welkom, {naam}"}

@app.post("/inloggen")
async def inloggen(naam: str = Form(...), wachtwoord: str = Form(...)):
    with SqliteDict("gebruikers.db") as db:
        if db.get(naam) == wachtwoord:
            return {"bericht": "Ingelogd"}
    return {"bericht": "Naam of wachtwoord klopt niet"}
```

<Regel n={9}>
Het wachtwoord gaat letterlijk de database in, onder de naam van de gebruiker.
</Regel>

<Regel n={16}>
Inloggen vergelijkt wat de gebruiker intypt met wat er in de database staat. Staat de naam er niet in, dan geeft `db.get` `None`, en dat is nooit gelijk aan een wachtwoord.
</Regel>

</CodeUitleg>

Dat werkt. Het probleem zie je pas als iemand anders dan je server de database
in handen krijgt.

## Waarom dat gevaarlijk is

Databases lekken. Een fout in de code, een kwijtgeraakte back-up, een
beheerder die meekijkt, een laptop in de trein: vroeg of laat ligt de inhoud
ergens waar hij niet hoort. Staan de wachtwoorden er als gewone tekst in, dan
heeft wie het bestand opent meteen alle wachtwoorden.

En dat raakt niet alleen jouw site. Veel mensen gebruiken hetzelfde wachtwoord
voor hun mail, hun games en hun bank. Wie het wachtwoord van jouw gastenboek
heeft, probeert het daarna overal.

## Doe het na, met je eigen database

:::danger[Alleen je eigen database]
Doe dit **uitsluitend** met je eigen server op `127.0.0.1` en je eigen
database. Proberen de wachtwoorden van een ander te achterhalen is
computervredebreuk, en strafbaar.
:::

Start je server met de code hierboven. Maak daarnaast een los scriptje
`registreer.py` dat drie gebruikers aanmaakt, net zoals een formulier dat zou
doen. Het gebruikt `httpx`, een module om verzoeken te versturen, net als in
[Te veel verzoeken](/docs/veiligheid/dos/zwakheid). Heb je hem nog niet,
installeer hem dan met `python -m pip install httpx`.

<CodeUitleg>

```python showLineNumbers
import httpx

adres = "http://127.0.0.1:8000/registreer"

gebruikers = [("sara", "welkom123"), ("alex", "Zonnebloem-Fiets-42"), ("noor", "welkom123")]
for naam, wachtwoord in gebruikers:
    antwoord = httpx.post(adres, data={"naam": naam, "wachtwoord": wachtwoord})
    print(antwoord.json())
```

<Regel n={5}>
Drie gebruikers, elk een tuple van naam en wachtwoord. Sara en Noor kozen hetzelfde, zwakke wachtwoord.
</Regel>

<Regel n={7}>
`httpx.post` stuurt een formulier: `data` zijn de velden, precies zoals `name="naam"` en `name="wachtwoord"` in een HTML-formulier.
</Regel>

</CodeUitleg>

Draai het in een tweede terminal. Je ziet drie keer een welkom. Speel nu de
aanvaller die de database te pakken heeft gekregen. Dat is een tweede scriptje,
`lees_database.py`, dat het bestand opent en alles laat zien:

```python
from sqlitedict import SqliteDict

with SqliteDict("gebruikers.db") as db:
    for naam, wachtwoord in db.items():
        print(f"{naam}: {wachtwoord}")
```

Uitvoer:

```
sara: welkom123
alex: Zonnebloem-Fiets-42
noor: welkom123
```

Alles staat er, leesbaar. Er is geen inbraak in je server voor nodig: het
bestand openen is genoeg.

## Dan maar een hash?

Een bekende eerste verbetering is een **hash**: een berekening die van een
wachtwoord een lange, onleesbare code maakt, en die niet terug te rekenen is.
Python heeft er een ingebouwd, `sha256`. Zo ziet een `sha256`-hash eruit:

```python
import hashlib

wachtwoord = "welkom123"
print(hashlib.sha256(wachtwoord.encode()).hexdigest())
```

Uitvoer:

```
2a5c5f2623024ce3de6fe7dc8f5e13ca55b7aadc13174254b40af574e37018c1
```

`.encode()` maakt van de tekst bytes, want daar rekent `sha256` mee, en
`.hexdigest()` schrijft de uitkomst als tekst. Zet het in je endpoint: regel 9
wordt `db[naam] = hashlib.sha256(wachtwoord.encode()).hexdigest()`, met
`import hashlib` bovenaan.

Gooi `gebruikers.db` weg, start je server opnieuw en draai `registreer.py` en
`lees_database.py` nog een keer:

```
sara: 2a5c5f2623024ce3de6fe7dc8f5e13ca55b7aadc13174254b40af574e37018c1
alex: 9c6514b2297031c14bc3968b0dc45fc0ca22d6795a835f5abc8c08a9eb6d250d
noor: 2a5c5f2623024ce3de6fe7dc8f5e13ca55b7aadc13174254b40af574e37018c1
```

Dat ziet er veilig uit. Maar kijk naar Sara en Noor: dezelfde code. Wie de
database heeft, ziet dus meteen wie hetzelfde wachtwoord gebruikt.

En het kan erger. Terugrekenen kan niet, maar raden wel: bereken de hash van
een wachtwoord dat veel mensen kiezen, en kijk of die ergens in de database
staat. Dat doet `raad.py`, met een lijstje van vijf veelgebruikte
wachtwoorden:

```python
import hashlib

from sqlitedict import SqliteDict

veelgebruikt = ["123456", "wachtwoord", "qwerty", "welkom123", "voetbal"]

with SqliteDict("gebruikers.db") as db:
    for naam, opgeslagen in db.items():
        for poging in veelgebruikt:
            if hashlib.sha256(poging.encode()).hexdigest() == opgeslagen:
                print(f"{naam} gebruikt {poging}")
```

Uitvoer:

```
sara gebruikt welkom123
noor gebruikt welkom123
```

Echte aanvallers doen precies dit, met lijsten van miljoenen gelekte
wachtwoorden. En `sha256` is gemaakt om snel te zijn: een gewone laptop
rekent er miljoenen per seconde uit. Alleen het lange, ongewone wachtwoord van
Alex blijft over.

Dat is de zwakheid: een wachtwoord als gewone tekst is meteen leesbaar, en een
snelle hash is met een woordenlijst binnen een paar seconden te raden.

## Er gaat iets mis

Je draait `lees_database.py`, en er verschijnt niets. Geen foutmelding, maar
ook geen gebruikers.

**Oorzaak:** het script draait in een andere map dan je server.
`SqliteDict("gebruikers.db")` zoekt het bestand in de map waarin je het script
start, en bestaat het daar niet, dan maakt hij stil een nieuwe, lege database
aan. Die heeft geen gebruikers. Kijk maar: in die map staat nu een tweede
`gebruikers.db`.

**Oplossing:** zet de scriptjes in dezelfde map als `main.py`, start ze vanuit
de terminal in die map, en gooi de lege `gebruikers.db` in de andere map weg.

## Opdrachten

### Opdracht 1: Predict - Twee keer hetzelfde

Een vierde gebruiker, Tim, registreert met het wachtwoord `welkom123`. Je
server bewaart `sha256`-hashes.

**Vraag:** welke code staat er in de database bij Tim?

<details>
<summary>Tip</summary>

Een hash hangt alleen af van wat je erin stopt.

</details>

<details>
<summary>Antwoord</summary>

Precies dezelfde als bij Sara en Noor:
`2a5c5f2623024ce3de6fe7dc8f5e13ca55b7aadc13174254b40af574e37018c1`. Hetzelfde
wachtwoord geeft altijd dezelfde `sha256`-hash, en dat verraadt wie hetzelfde
wachtwoord heeft.

</details>

### Opdracht 2: Investigate - Kun je Alex vinden?

Zet het wachtwoord van Alex in de lijst `veelgebruikt` en draai `raad.py`
opnieuw. Wat zegt dat over de lijst die een aanvaller gebruikt?

<details>
<summary>Antwoord</summary>

Nu vindt het script ook Alex. Een woordenlijst vindt alles wat erin staat, en
niets wat er niet in staat. Aanvallers vullen hun lijsten daarom met
wachtwoorden uit eerdere lekken. Een lang, ongewoon wachtwoord dat nog nergens
gelekt is, staat in geen enkele lijst. Maar daar mag je niet van uitgaan: de
volgende stap zorgt dat ook zwakke wachtwoorden veel lastiger te raden zijn.

</details>
